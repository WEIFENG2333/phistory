# 简体中文翻译评测

评测日期：2026-09-06。使用真实归档与用户指定的 SiliconFlow API，对比 `deepseek-ai/DeepSeek-V4-Pro` 和 `zai-org/GLM-5.3`。这是本项目的工程验收，不是模型排行榜；有效 JSON、完整占位符和中文字符都不能证明语义正确。

本轮使用 GLM-5.3、通用提示词 v11 和显式 4096 思考预算。模型选择来自 v9 及此前的实测；v10 增加明确的保留状态和具体校验反馈，避免用更多代码特判处理每种句子。GLM 在否定、工具名、精确标签和复杂代码说明上较可靠，代价是更高延迟；保留 DeepSeek 作为显式可配置选项，不在重试时悄悄切换模型。这些有限样本不代表全库语义质量保证。

全量历史回填已完成，当前 Runtime 无待译条目；本轮用量保持在 200 元预算内。Static 已退出翻译范围，对应译文数据已删除；本文后面的 Static 样例仅保留为历史评测记录，不再进入默认评测或回填。费用测算与调用明细见 [成本审计](translation-cost.md)。

上一轮成本实验对比了当时待译 Runtime 队列的 62 段：1024 思考预算在三个普通标题/短句上误选 `preserved`；请求关闭思考仍产生实际 reasoning Token，且一个批次两次超时。每批 32 段的三个样本共 96 段，结构全部通过，人工仍发现 MiniMax 普通英文残留。正式回填因此保持每批 12 段、4096 思考预算，只对提示词作下述通用边界补充。

## v11 回填前复核

v11 只在【保留】增加一句通用边界：保留范围止于具体名称或字面量；同句的普通动作、角色说明和标题文字仍需翻译。没有增加特定句子规则或扩大术语词表。旧 v10 缓存继续有效。

实际复测此前六组共 62 段，再加四个之前出现保留范围过宽的 MiniMax 样例，全部经过 API 调用与逐段对照阅读。62 段的条件、否定、数字与工具名保持，边界样例中普通动作词的漏译有改善；仍记录了七个局部措辞、例子翻译或换行反馈，交给已有的模型修订入口处理。66/66 结构通过不等于不存在语言问题。

正式回填采用每批最多 12 段、6,000 字符、4096 思考预算，未采用较便宜但有误保留的 1024 配置。59 个已审读且无需修订的试译条目直接入库复用，未重复调用。全量期间另做跨 14 Agent 的早/中/新与正文、标题、工具参数审读，并单独检查模型判定为 preserved 的新增条目。

审读中发现某些初始 12 段批次的末两段出现相邻内容错配，结构校验没有阻止它们。因此对所有这类初批末两段做了辅助模型对应检查：先用已知错配与正常样本验证检查器，再按当前词典内容指纹仅检查新增或变动的段对。模型只提出问题，不直接改词典，也不作为语义全量放行者；每个报警仍由开发代理对照完整原文判断。最终检查范围为 738 对、1,476 段，开发代理确认 8 处问题（DSH 4、Hermes 1、OpenClaw 3），通过局部 feedback 重译后再次逐句复核；未报警项另对照阅读 14 对。其他段落没有被这个专项检查覆盖。客户端始终按响应键绑定原文哈希，没有发现按对象键顺序错配的代码缺陷，也不把未经验证的服务端排序猜测写成原因。

所有本轮审读发现的问题都交给正式客户端的 feedback 入口修订，没有直接手写中文替换。修订结果也会产生新问题：例如 MiniMax 的“阈值之内”改变门槛含义、Hermes 增加原文没有的“添加评论”、OpenClaw 增加原文没有的“保存”动作。这些候选被拒绝，再提供具体意见，接受最终忠实的模型结果。本轮最终有 53 个唯一条目接受了经审读的模型修订，所有待处理反馈均已关闭。全局提示词没有为这些句子继续加特化条款。

另改进参数上下文：附上属性路径与完整类型结构，保留 number/null 等联合类型，避免重复 description 被末尾 null 分支覆盖。真实 API 在没有针对该句的修订提示时，将“files to skip”准确理解为分页所跳过的文件数。上下文不进入文本哈希，因此不会因这项改进重新翻译既有历史数据。

输入为 `{"segments":[{"id":"0","text":"原文","context":"邻近章节或工具说明"}]}`，当前输出为 `{"translations":{"0":{"text":"译文","status":"translated"}}}`。整段无需翻译时返回 `preserved`，且结果必须与输入完全一致；含代码的自然说明仍应完整翻译。上下文包含章节/工具说明及参数的属性路径和类型结构，只用于消歧，不并入正文。段内指令和 JSON 都是待译材料，不执行它们。

正式客户端使用动态 strict JSON Schema：每个短 ID 必须对应完整的 text/status 条目，不允许额外键，并拒绝重复 JSON 键。此前两模型均通过实际 Schema 探针，v10 的 GLM 也已实测，没有悄悄降级为普通 JSON 模式。该格式和思考预算参数见 [SiliconFlow 官方接口文档](https://docs.siliconflow.cn/docs/api/chat-completions-post)。

## 语义检查中发现的真实问题

- DeepSeek 在通用 v8/v9 中多次把 `do not provide explanations` 翻成“无需解释”，把禁止弱化成没有义务；通用否定示例没有使它稳定修复。GLM 已返回的对应样本正确使用“不要提供解释”。
- DeepSeek 把工具名 `workflow` 译成普通“工作流”，把精确 UI 标签 `"(Recommended)"` 和 `"Other"` 翻成中文，并把“向用户提出问题、请求回答”误读为“请求用户输入问题”。GLM 核心样本保留标签，主客体正确。
- 压缩的 OpenClaw 技术说明中，DeepSeek 将 `clean context` 理解为清理动作，将自动化语境的 `Promote` 译为“推广”。GLM 有界思考返回的上下文状态更准确，保留不确定的 `Promote`，但仍存在生硬措辞和未译的普通英文词。
- 在代码说明中，DeepSeek 将“取自 result.content 的一个 ImageContent 块”译成“ImageContent 中的 result.content 块”，说明代码本身原样保留仍不能保证周边关系翻译正确。
- 早期大批次曾漏条目、重编号，并把一段授权顺序摘要成相反意思。失败原始响应保留用于审阅，没有写入正式翻译数据。

这些差异是最终模型选择的依据，不能仅按中文比例、格式通过率或延迟选型。有限样本也不足以声称某模型的所有译文更好。

## 最终候选验证

v9 的 GLM 2048 预算面板含 12 条风险回归与 10 条新增样本，22 条全部通过结构检查，但逐条阅读发现其中两条仍有语义问题：OpenClaw 的 `Promote` 又被译成“推广”，工具说明再次出现用户输入问题的主客体歧义。因此没有把 22/22 的结构通过率作为语义通过率。

相同核心三条改为 4096 预算后，`Promote` 保留原词，工具介绍译为“就一到三个简短问题请求用户输入”，标签保持原样。另三条代码描述、软换行、Markdown 围栏正文在 4096 下通过；代码类型与集合关系正确。新增三条 Schema 用 2048 与 4096 的语义接近，后者主要改善少量措辞，因此不能声称增加预算对所有段落都有明显收益。

补充真实完整参数 Schema 作为上下文后，同一工具介绍译为“通过一到三个简短问题请求用户输入”，只使用了 1096 个推理 token，耗时 17.35 秒。这表明相邻字段说明能帮助消歧；独立一句话的翻译质量并不等于包含完整上下文时的质量。

完整候选原文与译文位于本机 `final-v9-glm-replayed-review.*`；该文件使用修复后的强调/缩进还原逻辑回放相同模型响应，没有重新请求或手工润色译文。原始响应仍保存在各 `*-batch-*.json` 文件中。4096 定向结果见 `core4096-v9-glm-*`、`structure-v9-glm-*`，新增样本预算对照见 `budget-v9-glm-*`。

## 失败处理与验收边界

代码保护并还原反引号字面量、路径、URL、模板、强调、换行和相邻缩进。纯代码等无需翻译的整段由模型返回 preserved，并以输入完全相等校验。ID、占位符、数字、结构或明显长度异常会触发具体反馈和有限轮重译，失败内容不会覆盖已有合格缓存。结构校验只能发现部分错误，不能自动证明语义忠实。

标题、正文、工具和参数的自然说明应翻译；机器字段、精确输入和返回值保持原样。已有中文保持不动，混合段落只译外文。Trace 原始证据文件不重写；页面展示译文并保留原文入口，缺失翻译继续回退原文。

全库覆盖率、缺失条目和页面效果另有完整性及浏览器验收；样本审阅不等于所有历史段落均逐字审阅。模型偶发错译和生硬表达仍是边界，保留原文、内容哈希和提示词版本便于定位及定向重译。
